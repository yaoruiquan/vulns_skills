## 2. `form_context.json` 字段

浏览器填表阶段只读取 `/tmp/vulns-skills/phase2-ncc-report/form-contexts/YYYY-MM/DAS-ID/form_context.json`。`extract_vuln_data.py` 是底层提取脚本，不直接作为浏览器阶段的数据源；运行时 JSON 不写入正式提交材料目录。

| 字段 | docx 来源 | 说明 |
|----------|-----------|------|
| `title` | `漏洞名称` | 对应页面“漏洞名称” |
| `description` | `漏洞描述`、`漏洞简介` | 对应页面“漏洞描述” |
| `impact` | 固定规则 | 对应页面“漏洞危害”，固定填写“见附件” |
| `vuln_type` | `漏洞类型` | 仅作为类型判断依据，页面实际选项需人工确认一次 |
| `business_type` | 固定规则 | 对应页面“漏洞业务类型/漏洞类型”，固定为 `通用型漏洞` |
| `detail_category` | `漏洞详细分类`、`漏洞类型`、标题、描述综合判断 | 对应页面“漏洞详细分类”；必须是下方 NCC 允许选项之一 |
| `target_type` | `影响对象类型`、标题、产品、漏洞类型推断 | 对应页面“影响对象”；必须是下方 NCC 允许选项之一 |
| `vendor_country` | `厂商所属国家`、`产品厂商国家`、厂商/产品名推断 | 对应厂商国家/地区下拉；无法判断时默认“中国大陆” |
| `unit_name` | `漏洞厂商`、`影响厂商`、`厂商名称`、标题推导 | 对应页面“漏洞厂商”；原字段为“其他”时从标题/产品推导，如 `xl2tpd` |
| `affected_product` | `影响产品`、`受影响实体`、`产品名称` | 对应页面“影响组件” |
| `version` | `影响版本`、`受影响实体版本号`、`版本号` | 对应页面“影响版本”；会从“已在 1.3.20 版本复现”中提取 `1.3.20` |
| `url` | `漏洞URL`、`漏洞定位` | 对应页面“漏洞 URL” |
| `verification` | `漏洞验证过程`、`验证过程`、`漏洞验证` | 可作为补充说明 |
| `poc_text` | 固定规则 | 对应动态 PoC/POC详情字段，固定填写“见附件” |
| `temporary_solution` | `临时解决方案` | 对应“修复方案说明”候选内容 |
| `formal_solution` | `正式解决方案`、`修复方案` | 对应“修复方案说明”候选内容 |
| `submit_date` | `提交日期` | 仅供参考，不直接当作“发现日期” |
| `is_0day` | `是否0Day漏洞`、启动提示参数 | 对应页面“是否0Day漏洞”，必须在准备阶段明确为“是”或“否” |
| `is_original` | `是否为原创漏洞`、`是否原创`、启动提示参数 | 对应页面“是否原创/是否为原创漏洞”，必须在准备阶段明确为“是”或“否” |
| `docx_path` | 材料目录 | 当前使用的源 `docx` |
| `upload_zip_path` | CNVD 材料 `exp/*.zip` / `poc/*.zip`，或无现成 zip 时的 CNVD 材料目录自动打包结果 | 复制/生成到 `/tmp/vulns-skills/phase2-ncc-report/upload-zips/<DAS-ID>/NCC-*.zip` 后用于上传 |
| `upload_zip_prepared_path` | 运行时 zip | ffmpeg 压缩前的运行时 `NCC-*.zip` |
| `upload_zip_size_mb` | 运行时 zip | 最终 `upload_zip_path` 的大小，单位 MiB |
| `upload_zip_limit_mb` | `.env` | NCC 上传限制，默认 `50` |
| `upload_zip_within_limit` | 脚本判断 | 最终 zip 是否不超过限制 |
| `upload_zip_compressed` | 脚本判断 | 是否生成并改用 `NCC-*-compressed.zip` |
| `upload_zip_compression` | 脚本判断 | ffmpeg 压缩详情、使用档位和警告 |
| `upload_zip_source_path` | CNVD 原始 zip | 仅用于追溯，不直接上传 |
| `screenshot_paths` | `exp验证图片/*`、`poc验证图片/*`、`screenshots/*` | 仅记录；默认不单独上传，避免替换 zip |
| `video_paths` | `exp验证视频/*`、`poc验证视频/*`、`videos/*` | 仅记录；默认不单独上传，避免替换 zip |
| `browser_defaults` | 脚本推导 | 固化“0Day/原创=是或否”、二进制动态字段、附件策略等页面默认规则 |

## 3. 当前填写规则

| 平台字段 | 规则 |
|----------|------|
| 是否0Day漏洞 | 使用 `is_0day`；准备阶段必须用 `--is-0day 是/否` 或 Word 字段明确，给“是”就选“是”，给“否”就选“否” |
| 是否为原创漏洞 | 使用 `is_original`；准备阶段必须用 `--is-original 是/否` 或 Word 字段明确，给“是”就选“是”，给“否”就选“否” |
| 发现日期 | 以页面允许的日期控件或当前材料确认，不直接使用 `提交日期` 硬填 |
| 漏洞业务类型/漏洞类型 | 固定保持/选择 `business_type=通用型漏洞`，不要选“事件型漏洞” |
| 影响对象 | 优先根据 `target_type` 选择 |
| 厂商所属国家/地区 | 使用 `vendor_country`；无法判断时为“中国大陆” |
| 漏洞厂商 | 使用 `unit_name` |
| 影响组件 | 使用 `affected_product` |
| 影响版本 | 使用 `version` |
| 漏洞名称 | 使用 `title` |
| 漏洞详细分类 | 使用 `detail_category`；二进制溢出类固定优先选“二进制”，不要保留平台默认“SQL注入” |
| 漏洞 URL | 使用 `url`；如果材料里就是 `http://none`，保持原样，不要自行改写 |
| 漏洞描述 | 使用清洗后的 `description`，不保留 Markdown 标记、代码块和“经恒脑AI代码审计智能体分析：”前缀 |
| 漏洞危害 | 固定填写“见附件” |
| 修复方案 | 根据页面单选按钮选择，修复方案说明固定填写“见附件” |
| 二进制动态字段 | 选择“二进制”后补填 `browser_defaults.binary_required_fields` 中的“版本号”“触发位置”“PoC” |
| 漏洞附件 | 默认只上传 `upload_zip_path`；不要补传 docx/截图/视频，避免单文件控件替换 zip |

## 4. 影响对象允许选项

`target_type` 只能使用以下 NCC 页面选项。脚本会优先使用 Word 中的合法值；否则根据标题、产品名、漏洞类型推断。

操作系统、应用程序、WEB应用、数据库、网络设备（交换机、路由器等网络端设备）、安全产品、智能设备（物联网终端设备）、区块链公链、区块链联盟链、区块链外围系统、车联网、工业控制系统。

## 5. 厂商国家/地区规则

`vendor_country` 对应页面的厂商国家/地区类下拉。脚本会优先读取 Word 中的 `厂商所属国家`、`产品厂商国家`、`所属国家`、`国家/地区` 等字段；否则按厂商/产品关键词判断。无法可靠判断时默认“中国大陆”。

常见自动判断：Apache、ActiveMQ、APISIX、SeaTunnel、dotCMS 等优先“美国”；D-Link 优先“中国台湾”；DataGear、UJCMS、novel-plus、rebuild、安恒相关默认“中国大陆”。

## 7. 不要硬填的内容

- 不要把 `提交日期` 当成 `发现日期` 自动写入。
- 不要保留页面默认“漏洞详细分类=SQL注入”；二进制溢出类必须切到“二进制”。
- 不要把 PoC 文本按 textarea 顺序硬填；必须按 label 填到“PoC”，触发位置填到“触发位置”。
- 不要自行编造厂商官网、修复方案或验证过程；PoC、漏洞危害、修复方案说明统一填“见附件”。
